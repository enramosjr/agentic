## Problem and outcome

Mechanical requirement evidence currently sorts by raw timestamp string, record filename and ledger index. Producers truncate completion timestamps to whole seconds. Two checks in different tasks can therefore be ordered by filename rather than execution completion. implementation-7.md records a passing handoff rerun selecting older committed evidence and remaining STALE; its fixture avoids the collision by spacing tasks1.05 seconds apart. No fresh reproduction was run for this draft, and no newly demonstrated false VERIFIED is claimed.

The recovered original area1 spec explicitly chose timestamp then filename. This proposal strengthens that accepted contract; it does not rewrite its approval or historical evidence. The outcome is a bounded mechanical ordering repair: distinguish recorded subsecond completion times and refuse to assert VERIFIED when recorded precision cannot establish which matching execution is latest.

Greater precision alone is insufficient. A legacy value `2026-10-28T01:00:00Z` was truncated to seconds and could describe completion anywhere within that second; it must not automatically rank before a new `.500000Z` value in the same second. Likewise ledger append/batch publication order is not execution completion order. The proposal uses the precision carried by each timestamp and makes overlap explicit uncertainty.

This contract orders **recorded UTC completion times**. It cannot discover arbitrary clock reversal or misdated records across independent processes/hosts from timestamps alone. Eliminating that separate limitation would require a separately approved durable ordering/event-metadata contract. It is an explicit approval choice below, not an assurance this bounded repair can supply.

## Users and scenarios

- A maintainer runs the same obligation in two tasks within one second. An earlier PASS and later FAIL must yield FAILED; the reverse must yield VERIFIED when freshness holds, irrespective of record names.
- An exact-match delta convergence and an explicit obligation run overlap. The command's recorded completion, not batch publication time, determines precedence when precision distinguishes them.
- A reader combines old second-resolution records with new fractional-resolution evidence. A same-second overlap is reported as UNVERIFIED rather than resolved by fabricated precision.
- An adopter retries Verify. An ambiguous matching evidence set blocks through the existing UNVERIFIED rule; neither attestation nor risk acceptance can waive it.

## Terms and approved decision defaults

**Matching evidence** means the existing exact stable requirement label, command argv and ordered evidence input declaration match, after the existing record eligibility/audit rules. Unrelated commands, IDs and input identities cannot influence ordering. Recorded execution outcomes do not participate in deciding which record is newest.

**Timestamp grammar:** valid ordering timestamps are UTC `YYYY-MM-DDTHH:MM:SSZ` or `YYYY-MM-DDTHH:MM:SS.<1–6 digits>Z`, with actual calendar/time validation. Newly produced mechanical `req:` entries use exactly six fractional digits. Offset forms, missing timezone, invalid dates, missing/nonstring/empty timestamps and more-than-six fractional digits are unsupported for this contract and fail closed when relevant. This consciously strengthens validation that ledger.audit currently does not perform; it does not rewrite legacy records.

**Precision interval:** a value represents a half-open interval starting at its recorded time and extending by its least represented unit. Whole-second legacy values cover one second; six fractional digits cover one microsecond. Equivalent zero-padded spellings have the same lower endpoint but retain their represented precision. Comparison must not use floating-point rounding. A single valid matching candidate can be evaluated normally. With several candidates, one is provably latest only when its interval starts at or after every other distinct candidate interval ends. Otherwise latest order is unresolved. Distinct entries in one record get the same treatment: index cannot substitute for unrecorded completion order.

**Duplicate representation:** the existing loader's replacement of the active task's published record by its active state must prevent counting that same representation twice. Separate executions at different task/index identities are distinct events even if their entry bytes happen to be equal. Do not collapse them merely to manufacture certainty. Filenames/indices remain provenance identifiers, never chronological tiebreaks.

**Ambiguity result:** use existing UNVERIFIED, basis none and no selected evidence (`evidence: null`), with a reason naming the ordering uncertainty and affected record/index identities. For well-formed overlapping timestamps, recommend an explicit fresh obligation run after the ambiguous intervals; only a provably later new candidate resolves the overlap. Missing/malformed relevant metadata is unorderable and must name the affected record and require evidence reconciliation; do not promise that a rerun alone can dominate unknown time. No automatic record deletion, mutation, migration or command execution occurs.

The PASS/FAIL ordering fixtures may deliberately use a controlled test-only outcome source, representing a check that can succeed or fail on identical recorded inputs. They must declare that controlled nondeterminism, show the actual process exits, and verify that command argv, selected file bytes and runtime fingerprint remain identical across the pair. They must not present an omitted mutable application-data read as proof of complete input scope or let an unrelated freshness mismatch explain an expected ordering result.

- R2: New mechanical `req:` entries produced through `assure --run`, direct `lifecycle.py run req:<ID> -- ...`, and exact-command delta convergence MUST record six-digit fractional UTC completion time after the command finishes and before later batch publication. A single legacy candidate and disjoint legacy intervals MUST remain usable under existing freshness rules.
- R4: Missing, malformed, unsupported or nonstring timestamp data on an otherwise eligible matching candidate MUST prevent choosing a possibly older PASS and MUST yield the explicit metadata-reconciliation result, without crashing. - R7: The shipped lifecycle guide MUST state completion-time/precision ordering, uncertainty diagnostics/remediation, the legacy/malformed/clock-reversal limits and absence of historical migration.
