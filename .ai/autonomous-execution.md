# 9. Autonomous Execution Protocol

This protocol lets agents carry long, multi-phase work across many sessions without relying on conversation history. **The repository is the memory.** Conversation context can vanish at any moment, so anything that matters is written to the repository as soon as it is known. The protocol applies whenever `knowledge/project/work-queue.md` exists. Create it with `okf.py init --autonomous`. Everything in root `AGENTS.md` §1–§8 still applies inside every iteration.

It lives outside `AGENTS.md` because harnesses load `AGENTS.md` into every agent, including workers and reviewers that never need it. Load it by section: `python3 .ai/scripts/okf.py show .ai/autonomous-execution.md --section '9.5'`. Workers given an `okf.py handoff --task` brief do not load it.

## 9.1 Where project state lives

| Concern | Authoritative home | Rule |
|---------|--------------------|------|
| Vision, scope, goals, non-goals, constraints, completion criteria | The project's product or boundary docs in `knowledge/project/` | Stable. Not a task tracker. |
| Phases, milestones, roadmap, dependency order | The project's roadmap doc in `knowledge/project/` | Defines phases and their exit criteria. |
| Requirements and acceptance criteria | `knowledge/capabilities/` and `knowledge/specifications/` | Canonical. The queue references them and never copies them. |
| Work queue: tasks, state, ownership, decomposition | `knowledge/project/work-queue.md` | Execution state of open work only (§9.3). |
| Closed tasks | `knowledge/project/work-queue-archive.md` | Written by `okf.py queue --archive`. Append-only. |
| Recovery checkpoint | `knowledge/project/status.md` | Overwritten in place, about 60 lines at most (§9.6). |
| Architecture decisions | The ADR register in `knowledge/project/` | One entry per significant decision (§9.7). |
| What happened and when | `knowledge/log.md` and `knowledge/history/` | Append-only. |

Do not create parallel root files such as `PLAN.md`, `STATUS.md`, `PROJECT.md`, `DECISIONS.md`, or a `docs/` tree. If a project lacks one of the docs above, create it inside the bundle with `okf.py new`.

**Run branch.** The work queue, its archive, and `status.md` have one writer on the long-lived run branch where the driver runs. Task branches never edit these three files. The run branch is internal and has no separate PR: merge the execution-state commits for a milestone into that milestone's integration branch before marking its PR ready. Record the active milestone ID, integration branch, and existing PR URL in `status.md` so fresh sessions reuse them. The driver may run directly on the milestone branch; in that case the same writer owns execution state there.

## 9.2 Objective and stop conditions

The project objective is whatever the project's product docs and roadmap define. Agents do not invent one. The `Objective` section of `status.md` records the objective a human has set for the current run, or `none set`. With no objective set, the queue covers the whole roadmap.

A **run** continues until one of the following holds:

1. Every task needed for the objective is DONE (or CANCELLED with a decision), and the objective's completion criteria are verified.
2. No unheld task is READY or IN_PROGRESS, and every remaining unfinished task is blocked on an unavailable prerequisite or has an execution hold with a concrete resume condition. Report this as blocked, never completed.
3. The next step requires a destructive, irreversible, security-sensitive, or outward-facing action that §9.9 does not authorize.
4. A delivery, elapsed-time or qualification-attempt circuit breaker is reached. Preserve work and report the precise blocker; limits take precedence over keep-going instructions. Do not automatically restart the driver or replace it with an interactive continuation to reset limits.

A run is a series of **sessions**, each with a fresh context (§9.8). A session advances one bounded usable-flow batch in solo mode, or one batch round in orchestrated mode, with a safe checkpoint. A batch may span up to three sessions (see the ceiling below); context/time handoff preserves unfinished implementation rather than forcing full validation, and ending a session that way is how the run continues. Delivery-stall limits still apply to unfinished batches; choose an achievable acceptance scope, close parts that genuinely pass, never manufacture DONE or restart to evade a limit.

**Batch ceiling (convergence rule).** A batch spanning sessions is not open-ended. Its acceptance is frozen when it is claimed: record the acceptance items (or lanes) and their count in `status.md`. Requirements discovered later, stricter re-readings of "parity" or "original" behavior, and new negative controls become new queue tasks (or a recorded decision), never silent growth of the active batch. **The session cap is mechanical.** Each implementation session that starts with a task active counts on that task's `Sessions` field in the work queue (the driver writes it; interactive sessions run `okf.py queue --record-session`). Three sessions is the cap. `autonomy_driver.py` refuses to start another session on a task already at the cap, `okf.py queue --record-session` refuses likewise, and `okf.py checkpoint` fails (not SAFE) when a task exceeds it. Because the count lives in the queue file, relaunching the driver with larger `--max-stalled`, `--max-sessions` or run budgets cannot reset it; only closing or splitting the task can. A task at the cap MUST be split into sub-tasks that each have their own acceptance, scoped gate and Evidence (new tasks start at zero); deliver the independently passing parts to DONE, and queue the rest as separate tasks (HELD or READY) with the failing evidence linked. A task whose acceptance cannot be met by one scoped gate in three sessions is mis-sized: decompose it (§9.3) before it starts. Parts that pass their own acceptance and review are closed as DONE with scoped Evidence as soon as they do, not held for the rest of the batch.

Other mechanical limits: `okf.py checkpoint` fails while an IN_PROGRESS task entry exceeds 3,000 characters or lists more than eight backticked acceptance commands (the cap only sees commands written in the entry; the session cap covers acceptance kept in a plan elsewhere). The driver rejects `--max-stalled` above 4. When a batch fails to converge, stop and report; do not authorize another continuation of the same unsplit task.

**Test proportionality.** Testing serves the product; it is not the deliverable. A run that mostly writes, repairs and re-records tests has stopped converging, and that is how a batch burns tokens indefinitely.

- Acceptance is a short list of user-visible success criteria. Each gets one E2E that fails when the criterion is unmet. A negative control is required only where a failure would otherwise pass silently, and one control per assertion class is enough. Do not multiply lanes, controls or sentinels per system, platform or variant; parametrize one test over the variants.
- "Parity" or "original behavior" is met by the user-visible checklist, not by porting every assertion, fixture and control of a prior harness. Porting a prior harness one-for-one is a separate, explicitly approved task.
- **Acceptance is autonomous or it is out of scope.** There is no human or manual qualification step. When a batch is claimed, every acceptance item MUST name a command that runs unattended and deterministically in the agent's own environment (virtual display such as `xvfb-run -a`, injected input events, a capture or null audio sink, fakes for devices). Never use the user's live display, audio or input devices: `shell_guard.py` rejects `DISPLAY=:0`/`:1` and `WAYLAND_DISPLAY`. An item that needs real hardware, a person, or an unavailable device is not part of the batch: record it at claim time as a scope decision or a separate BLOCKED task (§9.3), and never let completion wait on it.
- A check that fails for an environmental reason (display or focus, input devices, audio, timing) gets one repair. If the second run still fails environmentally, move the same assertion to a deterministic layer that exercises the same product code (for example drive the real event path with injected events instead of a physical device). If no such layer exists, drop the item from this batch's acceptance and record the dropped scope; do not keep repairing the environment and do not defer it to a human. A product defect found by such a check is still fixed.
- Do not rerun a long check to "re-sign" earlier evidence. Rerun only after a change to its inputs (§8.4) and move on.

A batch may also hand off a SAFE candidate with validation pending. The driver executes the submitted validation job between model sessions, then starts fresh evidence closure. Validation owns its command deadlines; it does not inherit the retired model's session deadline. The overall run deadline and live-chat lease still apply.

Evidence closure uses `--max-closure-seconds` (default 600), capped by the session target and remaining run budget, independently of the discovery progress query. Prepare the acceptance-to-command mapping during source review/focused checks; retain that independent review context for final results where independence permits. Do not keep a model waiting for deterministic tests. After actual SAFE delivery and relevant worker lifecycle reconciliation, write `{"head":"<current HEAD>","external_workers_released":true}` to the driver-supplied `OKF_CLOSURE_RELEASE` path and exit. This is one untracked handoff receipt, not another document/commit round. If closure is interrupted, the driver skips recovery only with newly evidenced DONE, full SAFE, this exact-HEAD receipt and no external worktree registered in that closure. Other interruption paths keep bounded recovery. Genuine delivered work resets idle/stall even when recovery is still needed; unrelated blocked ownership is never released by this receipt.

These are **not** reasons to end a session early or to stop the run: the project or a phase is large, much work remains, the work is complex, a phase just finished, or a task needs further decomposition (decompose it and continue). Do not ask whether to continue to the next READY task. Do not end a session with commentary about size or difficulty in place of work. Complexity triggers decomposition, not termination. Do the useful executable portion now rather than deferring a whole item because the batch might not fit. Do not commit unchanged execution facts merely to say "try later"; budget exhaustion is not an external blocker or delivery.

### Circuit breakers and qualification failures

Unattended implementation must use `autonomy_driver.py`, not an unbounded app conversation or repeated keep-going/goal continuations. Defaults are a 1,200-second session checkpoint target, a 3,600-second agent-execution run budget, and two consecutive implementation sessions without a newly evidenced DONE requirement. Session rotation is not a run stop. At the target the driver writes `OKF_HANDOFF_REQUEST` and emits a public handoff event with remaining queue count, active IDs and checkpoint state. Agents check this path at tool/wait boundaries, stop new dispatch, query workers for head/current command/completed checks/remaining work, report publicly, settle ownership and checkpoint. Healthy checks can finish within `--handoff-seconds` (default 180), always inside the original run budget. Never infer a hang from test silence or invent an ETA.

If the window expires, the driver stops and reaps its owned process group, preserves files and reports remaining work. A forced timeout, unsafe cooperative handoff, or unsuccessful session that left changed/unsafe work can start at most one records/ownership recovery session per run, capped at the handoff duration and remaining run time. Recovery consumes a session slot, does no new implementation or expensive validation, and must leave a SAFE checkpoint before a fresh implementation session resumes. Unresolved external ownership must fail recovery; repository checkpoint checks do not prove remote workers stopped. Interrupted sessions count toward the delivery-stall limit; recovery cannot reset it, the idle counter, attempts or elapsed time. Failed recovery, a second forced interruption, exhausted session/run/delivery limits, lost chat supervision or a clean command failure stops the run without automatic restart. A cooperative handoff remains subject to normal delivery/idle limits.

PR synchronization is skipped during recovery and checked against the remaining budget before another implementation agent launches; it is not itself forcibly terminated. These are time/delivery controls, not a model token-budget meter. Detached remote work or model sessions not launched by the driver are outside its process control and must be reconciled by the orchestrator before reassignment.

**Discovery and phase controls.** Default `--max-discovery-seconds 120` requests concrete progress via `OKF_PROGRESS_REQUEST` if no source activity is observed in the run worktree or registered owned worker worktrees. Report inspected code/commands, findings and next executable action while continuing useful investigation/implementation. This is advisory, separate from `OKF_HANDOFF_REQUEST`, and does not retire a worker. Register workers before dispatch via `autonomy_validation.py track-worker`; registration retains its initial HEAD so it cannot reset the observation baseline. Knowledge/Markdown/text/log edits do not count as source progress or reset the idle limit; evidenced delivery does. Session/run limits remain binding. Source activity is not delivery evidence. Evidence-only closure uses its separate closure target and does not require artificial source edits.

The first managed-validation handoff is a phase transition: it neither increments nor resets idle/delivery counters. Later submissions without delivery increment the stall counter, with one narrow exception for verified deterministic source repair. A repair manifest binds the immediately preceding unchanged FAIL result, names its first regression command and retained independent source review, and makes every full-gate command depend on that regression. The candidate must descend from the failed candidate with source changes, not records alone. The driver admits the bounded regression at the stall boundary; only a fresh PASS exempts this handoff's increment. Prior stalls are not reset. Failed proof at the limit stops before the full gate. Unchanged retries, PASS closure, timeouts and model-backed cases do not qualify. Records-only recovery cannot reset the limit. Validation completion or repair progress is not DONE; only evidence-reviewed queue closure resets the delivery counter. Run/session/qualification/custody limits remain binding.

For interactive supervised work, record the same time/attempt boundaries in the checkpoint and end the turn at them; repository prose is not an executable app-session limit. Do not claim that a driver update stopped an already running app turn. Use the app's stop control for that turn before resuming unattended execution through the driver.

Allow at most two failed fresh model-backed qualification cases for one slice per unattended run, including failures after changed freezes or in replacement threads. Retain the count and failure classes in the existing checkpoint; source fixes do not silently reset it. Preserve all evidence and original custody/retry limits. Diagnose the earliest failing contract mechanically; exercise the composed public user flow with explicitly mechanical evidence before another permitted genuine attempt. Never substitute that mechanical evidence for independent model-backed acceptance.

Ordinary deterministic CI failures, dependency advisories, code-generation drift and infrastructure checks that execute no fresh model-backed case do not consume that model-backed allowance. Once a genuine case starts, retain its original failure-class/custody/retry counting even if infrastructure fails. Retain results and repair deterministic checks within unchanged run/session/delivery-stall budgets. Validation manifests declare `validation_kind: deterministic` (the default) or `model-backed`; results retain that classification. A manifest containing a fresh model-backed case must use `model-backed`; do not relabel a genuine attempt to evade a limit. Classification does not reset any counter or waive a gate.

When the limit is reached, checkpoint the failed slice with its exact failure and next repair; do not manufacture DONE or waive a gate. If disjoint requirements can be delivered independently, split them into a smaller coherent batch with their own acceptance/required integrated gate, rather than keeping completed independent work hostage to repeated model-backed failures. Select other eligible work in the next fresh session. Source commits, new freezes, documentation and tests alone do not count as delivery; the driver requires newly DONE IDs with Evidence. A stall stop requires inspection, not an automatic wrapper restart.

## 9.3 Work queue format

Each task is a level-3 heading `### ID — Title` followed by `- Key: value` lines. Examples inside code fences are ignored. `okf.py validate` enforces the rules below (`okf.py --help` lists them).

| Field | Meaning |
|-------|---------|
| `State` | One of the states in §9.4. Named `State` so it does not collide with the OKF frontmatter `status`. |
| `Priority` | Integer, lower first; default 100. Ties keep queue order. |
| `Group` | Phase, milestone, or workstream name taken from the roadmap. |
| `Parent` | Parent task ID, for subtasks. A parent becomes READY only when all its children are DONE or CANCELLED. |
| `Depends` | Comma-separated task IDs that must be DONE first. |
| `Acceptance` | Links or IDs of the canonical acceptance criteria. Add objective sub-criteria as subtasks rather than rewriting the canonical ones. |
| `Validation` | The exact commands that prove the acceptance criteria. The batch plan separates focused worker checks from the full integrated gate without removing required coverage. |
| `Owner` | `agent-id@branch` while claimed. |
| `Evidence` | Link to the history record or log entry that proves DONE. |
| `Blocker`, `Unblock`, `Parallel` | What blocks the task, what would unblock it, and whether other work can proceed. |
| `Hold`, `Unblock` | Suspend dispatch of unfinished READY/NOT_READY/IN_PROGRESS work until a concrete resume condition changes. Holds preserve dependency state and require `Unblock`. |
| `Reason`, `Decision` | Why a task is DEFERRED or CANCELLED, and the ADR that decided it. |

Task IDs reuse the project's stable requirement or capability IDs where they exist. Subtasks append `.n`. IDs are never reused or renumbered.

**Archive.** `okf.py queue --archive` moves DONE and CANCELLED tasks to `work-queue-archive.md`, so every agent that reads the queue pays only for open work. Archived IDs stay reserved and still satisfy `Depends` and `Parent`. `okf.py queue --state DONE` lists them. Never edit or reopen an archived entry; add a new task instead.

## 9.4 Task states

| State | Meaning | Required fields |
|-------|---------|-----------------|
| `NOT_READY` | A dependency or child is still open (computed) | none |
| `READY` | All dependencies DONE, no open children (computed) | none |
| `IN_PROGRESS` | Claimed and underway | `Owner` |
| `BLOCKED` | Needs something currently unavailable | `Blocker`, `Unblock` (plus `Parallel`) |
| `DONE` | Acceptance met and §8.2 satisfied, with validation run in this change | `Evidence` |
| `DEFERRED` | Still valid, intentionally moved later | `Reason` |
| `CANCELLED` | No longer required | `Reason` (plus `Decision` when it removes a requirement) |

`okf.py queue` recomputes READY and NOT_READY from the graph, so write either one as `READY`. Only IN_PROGRESS, BLOCKED, DONE, DEFERRED, and CANCELLED are trusted as written. Writing code alone never makes a task DONE.

Before exiting when a limit prohibits all further action on a task, record `Hold` and its concrete `Unblock` condition; use BLOCKED for an unavailable external dependency. A held task remains unfinished and cannot satisfy dependencies. The driver skips held READY and IN_PROGRESS tasks, continues other eligible work, and reports held reasons without launching another model when nothing executable remains. Remove the hold only after verifying its resume condition, preserving original evidence and limits. An execution hold never hides dirty work or bypasses a SAFE handoff.

## 9.5 Execution loop

Each session advances one bounded batch through the applicable Gates 1–4 (`AGENTS.md` §6). Requirements remain the units of acceptance and evidence; batches are the units of integration and expensive validation, and milestones remain the units of PR scope. A session handoff is not a batch-completion or full-validation boundary.

### Batch selection and dependency waves

Select connected flows from this repository's objective, current roadmap, acceptance criteria and queue. Product-specific priorities belong in project knowledge and task briefs, not this reusable protocol. Prefer completing the next usable flow over isolated requirements in priority order. `okf.py queue --next` remains a dependency/priority view, not an automatic batch scheduler. Reconcile source-backed delivery evidence for the selected work before scheduling stale queue entries; do not turn that check into a repository-wide delivery audit or infer DONE from a capability document alone.

Reuse a batch's existing acceptance, dependencies and validation. Before dispatch record only task IDs, owners, worktrees and next focused checks; do not require another full plan, commit/push or SAFE certification first. Keep the complete coverage/command union current by integration/validation handoff, grouping its records with meaningful changes. Keep external prerequisites DONE. A NOT_READY requirement can join only when all its unresolved dependencies are earlier members of this batch. Start it only after those members are reviewed, merged into the milestone head and pass focused acceptance checks. This is provisional internal readiness, not queue READY or DONE; preserve `Depends`, keep started tasks IN_PROGRESS and leave their PR boxes unchecked until the batch gate passes. Canonical phase/research/security gates remain binding. If a batch cannot fit a bounded session, checkpoint its unfinished state and continue the same batch in a fresh session. Split only at an independently required acceptance/delivery boundary, not simply because one session ended.

**Continue implementation before full validation.** Keep the batch tied to the user's requested acceptance. Intermediate flows run focused checks and their own acceptance E2E; record them as provisional coverage. A part that is independently deliverable and passes its own acceptance and review is closed as DONE with scoped Evidence; do not hold it hostage to the rest of the batch. A SAFE implementation handoff records remaining acceptance, tested commits, focused results, deferred full commands and the next source action. It need not submit managed validation. Only submit the full gate once the planned batch acceptance is implemented and reviewed, or an explicit readiness/qualification boundary requires it. Do not accumulate extra planning or closure rounds to make this distinction. Time, session, delivery-stall and qualification limits remain unchanged; provisional progress never authorizes DONE.

**Reconcile validator upgrades at handoff.** Running drivers retain imported code and do not hot-load tooling updates. A resume with an incompatible legacy PASS fingerprint and no component hashes stops rather than silently repeating that command. Preserve its manifest/log hashes and independently review its tested candidate, environment and acceptance coverage; when submitting only missing checks, retain the combined coverage map and original receipts for evidence closure. Never rewrite an old digest to manufacture equivalence or reset a run budget to adopt new tooling.

Run independent lanes in each wave concurrently only with no dependency between them and disjoint owned files, shared prose, schemas, fixtures and mutable build/scratch resources. Assign shared registration/schema/interface wiring and the integrated branch to one integrator. Separate worktrees alone do not make overlapping edits independent.

### Focused checks and the integrated gate

**Disk-backed scratch is mandatory.** Use the repository's common Git directory `okf-scratch/` for all workflow temporary files, worktrees and build/test scratch. The driver and managed validator enforce `TMPDIR`, `TMP` and `TEMP` there for descendants, overriding inherited or manifest temp settings; do not override them or hard-code `/tmp`, `/var/tmp` or `/dev/shm`. Scratch preflight rejects system temporary paths, their symlinks and Linux tmpfs/ramfs mounts, and verifies writability without fallback. Startup reports the path and available disk space. Progress/ack files must also be outside system temporary storage. For interactive/focused commands, use `python3 .ai/scripts/timed_check.py --label NAME -- COMMAND`, which applies the same environment. Keep retained evidence in the supplied Git-metadata paths. Moving scratch changes validation inputs; reuse only receipts whose effective environment still matches. Preserve existing budgets and failed results; storage repair never authorizes an automatic restart.

**Preflight before the expensive gate.** At the first integrated candidate, check changed registry/tool inventories, schema/version and grant prerequisites, fixture prerequisites, and the real host's launch/configuration path. Use the existing clean-state startup diagnostic where available; otherwise add a neutral diagnostic to the owned host harness. It must assert actual initialization, required tool/schema discovery and unchanged authored state, and reject missing binaries/startup. Run it before the full suite, freeze or held-out staging. A transport preflight is not model-backed or product acceptance. Repair discovered public-contract gaps in their owning slice rather than rediscovering them during private qualification.

**Prepare independent custody before exposure.** For held-out/model-backed qualification, assign the eligible producer, independent judge, custody reviewer, integrator and records owner before anyone accesses fixtures. Record exclusions, allowed material and timestamped exposures under the accepted policy. Prepare neutral launch/schema configuration early; stage fresh probes only after the final reviewed implementation/binary/prompt/config freeze. Keep producer/judge/source-author independence and recipient restrictions intact.

Workers run focused builds and unit/contract tests during implementation, the acceptance-specific E2E once the change is complete, and after a merge only the checks whose inputs it changed. Reviewers use those results and narrow reproduction checks. Report exact commands/outcomes and explicitly list full required commands deferred to integration; do not stamp unrun commands as verified.

**Execute the full gate as a managed job.** After source review/integration, commit the resumable checkpoint with tasks IN_PROGRESS and validation pending, then submit the manifest described in the playbook using `autonomy_validation.py submit --plan PATH` and exit. The driver checks SAFE before running. The manifest pins HEAD, declares requirements and maps each unique argv command to coverage and a finite timeout, with optional explicit environment. Jobs are serialized in the candidate worktree; settle all mutable resource/writer ownership first. Each command can use the lesser of its timeout and actual remaining run time after `--validation-reserve-seconds` (default 60). Do not sum maximum timeouts to defer an otherwise executable gate. Only an already exhausted reserve causes BUDGET_DEFERRED before work; hitting the actual budget during the gate records BUDGET_EXHAUSTED, retains partial results and stops the run. Do not shorten tests or reset budgets to force completion.

The driver records results and private merged-output logs after each command, emits public start/result/heartbeat events, and stops the gate at the first failure or timeout. Candidate HEAD and tree cleanliness are checked before commands and at completion; drift invalidates the result and stops the run. Loss of supervision cancels/reaps the active command and durably marks cancellation while retaining prior results. Each request is single-use. Results live under the worktree's git metadata `okf-autonomy/<run>/<session>/`, outside tracked inputs. A fresh model gets the exact result path; PR synchronization is deferred until that evidence session can inspect the unchanged candidate. This executor cannot certify that a submitted coverage map includes every canonical acceptance criterion; independent evidence review remains required.

Resume retained validation with `autonomy_validation.py submit --resume RESULT_JSON` (optionally `--plan PATH` for corrected commands). It verifies prior manifest/log hashes, rejects invalidated jobs, and reuses only PASS/zero-exit receipts matching the whole command, effective environment and prerequisite input fingerprints. By default commands bind to the exact candidate; changed commits rerun those commands. Partial PASS is never a full gate or DONE. Do not add a records-only commit merely to resubmit the same candidate.

**Opt-in reuse across commits.** A deterministic command may declare `"inputs": ["src", "tests", "Cargo.toml", "Cargo.lock", "build.rs"]` using existing tracked files or directories, as literal repository-relative paths. Declare every source, harness, fixture, configuration, dependency and build input it consumes; directories include additions, deletions and file modes. Review the scope with the command's coverage before using it. Matching content fingerprints allow reuse after unrelated or records-only commits, preserving `tested_candidate` on each receipt. Missing paths, symlinks and submodules are rejected because their complete inputs cannot be established this way. Undeclared/unknown dependencies, mutable external inputs, generated artifacts without verified custody, commands that inspect Git HEAD, and exact-commit/host freezes MUST retain the default commit binding. Model-backed jobs cannot declare `inputs`. Prerequisites without declared inputs retain their commit binding and invalidate dependent receipts across commits. Changed commands, environments, validation kinds or prerequisite inputs rerun affected checks. This verifies declared input equivalence, not the completeness of the declaration. In the existing evidence report, record each expensive check's criterion, input scope and changed inputs or missing covering PASS (§8.4); one owner submits the integrated gate while other sessions reuse its results.

**Bounded independent lanes.** A manifest may set `max_parallel` from 1 to 8 (default 1). A command's `resources` list declares every mutable build/install/store resource it owns; overlapping names serialize. Omission is exclusive, while `[]` explicitly declares no shared mutable resource. `after` names prerequisite command labels; labels must be unique and the dependency graph acyclic. Preparation must precede artifact consumers. Failure, deadline, candidate drift or lost supervision cancels and reaps active peers. Result writes and supervisor events have one owner. Configure CPU/build-job and disk limits in command environments before raising concurrency; separate worktrees alone do not prove independence. Receipt fingerprints include prerequisite command inputs.

**Manifest template.** Copy this shape to `PATH` instead of reading `autonomy_validation.py` source; `submit --plan PATH` rejects what it cannot accept.

```json
{
  "validation_kind": "deterministic",
  "max_parallel": 2,
  "requirements": ["build", "unit", "e2e-a", "e2e-b", "records"],
  "commands": [
    {"label": "build", "argv": ["cargo", "build", "--release", "--locked"],
     "timeout_seconds": 1800, "coverage": ["build"], "resources": ["target"]},
    {"label": "unit", "argv": ["cargo", "test", "--locked"],
     "timeout_seconds": 1800, "after": ["build"], "coverage": ["unit"], "resources": ["target"]},
    {"label": "e2e-a", "argv": ["python3", "e2e/a.py"],
     "timeout_seconds": 1200, "after": ["build"], "coverage": ["e2e-a"], "resources": ["display-a"]},
    {"label": "e2e-b", "argv": ["python3", "e2e/b.py"],
     "timeout_seconds": 1200, "after": ["build"], "coverage": ["e2e-b"], "resources": ["display-b"]},
    {"label": "okf-records", "argv": ["python3", ".ai/scripts/okf.py", "records"],
     "timeout_seconds": 120, "after": ["unit", "e2e-a", "e2e-b"], "coverage": ["records"]}
  ]
}
```

Fixed-duration real-time checks (sustained captures, soaks) cannot be shortened, so serializing them multiplies the gate's wall time. Give each its own `resources` names (private display, audio sink, scratch and state directories) and raise `max_parallel` so they overlap, unless they truly share one mutable device; put every command on one shared resource name only when that is the real constraint. Keep timing-sensitive lanes on dedicated cores (§8.4).

**Share preparation, preserve assertions.** Harnesses that test an installed artifact can share one verified package prepared once per candidate. Sharing must retain package verification, a clean installed build, exact candidate/compiler/environment binding and artifact hashes. Each test owns fresh state. A sharded suite is complete only when every shard has run. Per-phase and per-test timing records identify the remaining expensive assertions. `validation_select.py --base REF` selects feedback checks using actual Cargo reverse dependencies when the repository is a Cargo workspace; packages named with `--core`, unknown paths and build inputs widen to the broad baseline. Its output is not a full-gate submission and does not waive slice-specific or milestone acceptance.

After all reviewed batch members and the connected-flow E2E are integrated, one validator runs the full required suite on that head once. Take the union of member `Validation`, applicable development/CI checks and the flow E2E, deduplicating identical commands and mapping narrower checks to a proven covering suite where appropriate. Preserve every required success criterion, package/install/failure-path check and qualification gate. Do not run the same expensive workspace/package suite per worker, reviewer, task merge and final records update. Only a complete PASS report on the tested integrated commit authorizes DONE and checked items. A failure keeps the batch unfinished; fix it, run focused regressions and rerun the invalidated integrated gate. Code, dependency, build-input or base changes invalidate affected evidence. Queue/status/OKF-only records updates need structural/index/whitespace checks, without rerunning unchanged product suites. Milestone-specific exit checks still run when the milestone is ready.

1. **Resume.** Use `okf.py handoff` startup readiness, which checks queue/Git state without scanning the entire knowledge corpus. It explicitly reports checkpoint NOT AUDITED. Resolve actual task/ownership/Git inconsistencies before affected edits; preserve uncommitted work. Unrelated documentation diagnostics run alongside implementation rather than blocking it. Resolve merge conflicts before mutating their integration branch (§9.9).
2. **Select.** Continue the active batch if one is recorded. Otherwise select and record the next usable flow and its dependency waves as above. Keep requirement IDs and canonical acceptance; decompose oversized work into bounded batches.
3. **Claim and start.** Reuse the milestone branch/PR and existing claim. Record changed eligible ownership with `State: IN_PROGRESS`, `Owner: <agent>@<task-branch>`, worktree and next check; dispatch from the existing durable milestone head without a preliminary commit/push or SAFE audit. Persist these records at the next source/integration/handoff boundary. Create internal task branches/worktrees containing required prerequisites; do not open task PRs.
4. **Gate 1.** Read the task's acceptance criteria and related docs by section, and load the persona and role by outline.
5. **Resolve decisions.** The implementation worker investigates and implements sufficiently specified work, including cross-module work. Use a separate planner only for a named unresolved decision that prevents safe implementation; resolve it by its tier (§9.7). Do not commission another plan to restate existing acceptance.
6. **Implement** (implementer role) with unit tests and the E2E required by §8.3.
7. **Check.** Run focused checks for the owned changes, the acceptance-specific E2E once they are complete, and OKF structural checks. Record deferred full commands. On failure, repair and rerun affected checks; never weaken a test.
8. **Review** (reviewer role), as a fresh subagent where the harness provides one, scoped to the task's diff. Fix confirmed findings.
9. **Synchronize** (Gate 3). On the task branch, update the capability, specification, and history docs, run `stamp verified PATH... --run CMD...` (it stamps only when CMD passes), and add an `okf.py log` entry.
10. **Integrate and close.** Merge reviewed task branches into the milestone branch, resolve conflicts and focused-test prerequisites before starting dependent waves. Repeat steps 3–9 for the remaining members of this same batch. Merge the current base before the final integrated gate and run its deduplicated full required suite once. Only after review and this gate pass, mark batch members DONE on the run branch with shared `Evidence` (milestone PR URL, tested commit and requirement-to-check coverage), archive, update the body checkboxes and overwrite `status.md` (`Active task: none`, completed batch/head and next batch). Run `okf.py checkpoint` until SAFE, then commit and push. A DONE batch does not make the milestone PR ready (§9.9).
11. **End the session.** Do not select another batch in this context. The next session starts fresh from the checkpoint (§9.8). If implementation is unfinished, preserve the active batch and focused evidence without running a full gate for the handoff; continue its next source action in the next session.

**One coordinated closure pass.** The validator returns one compact report: tested head, commands/outcomes, requirement coverage, evidence/freeze locations, independent decisions and blockers. Prepare the capability/spec/history/checklist updates during validation without asserting unrun PASS results. After required independent source/custody/host decisions arrive, the records owner completes Gate 3 and the queue/checkpoint/PR update together. Do not create separate review or agent rounds merely to restate accepted evidence or close prose. Substantive findings still require independent review and affected requalification. Reuse product results only with explicit tested-input equivalence; an exact host freeze may include Git HEAD and must not be bypassed because binary bytes match.

**Overlap nonblocking diagnostics.** Startup handoff uses the queue/Git subset of checkpoint checks, not a full OKF scan or clean-tree certification. Missing completion prose and unrelated document defects are not reasons to delay an otherwise owned/eligible implementation. Each driver model session runs one local read-only `okf.py validate --strict --json` diagnostic concurrently, storing its private log and advisory result under the session's git-metadata directory. It does not wait for this check before dispatch. The audit observes a changing tree, cannot certify the eventual candidate, and may be cancelled at retirement; the driver reaps its process group. Full checkpoint at actual handoff remains blocking and authoritative. Do not use advisory PASS to close a task or advisory FAIL to stop unrelated implementation.

Run independent environment diagnostics, neutral preflight preparation and documentation work alongside source work only with disjoint files/resources and no unmet dependency. Serialize Git mutations, overlapping edits and shared build/install/scratch resources. A check that requires the changed candidate runs after that candidate exists; do not repeat it as a generic startup ceremony. If a validation retry changes only command environment for the same committed candidate, reuse the existing checkpoint and submit directly, retaining prior failures and passing evidence. No new status/log rewrite, global startup audit or source edit is required. Known validation-result follow-ups are exempt from the source-activity discovery timer; existing overall/session/attempt/stall limits still bound them.

**Measure without extending the round.** Wrap expensive commands with `python3 .ai/scripts/timed_check.py --label <phase> -- <command>`. Retain its stderr timing record beside the existing command log. It preserves command output/exit status and records only label, UTC boundaries, elapsed seconds and outcome; do not put private content in labels. The driver emits the same record for each agent session. Add review/custody/closure timestamps to the existing evidence report, accounting for overlapping intervals. Timing PASS means the command exited zero, not that acceptance passed; the command's assertions and independent evidence remain authoritative. Compare the next batch's elapsed phases before optimizing package setup; preserve every installed-artifact assertion and clean build.

**Visible chat supervision is the default.** The launcher keeps its monitor turn open, posts public phase changes and at least one update per minute, then acknowledges the driver using the read → visible commentary → ack sequence in the playbook. Default driver startup requires fresh progress/ack paths; no model starts before the first acknowledgement. Heartbeats are generated locally every 30 seconds even while tests block. Missing/expired acknowledgement (90 seconds by default, checked at most every second) stops the owned agent group without retry. Do not run an automatic ack-renewal loop, let the child acknowledge itself, or claim a local progress file posts into app chat. Only explicit user-selected `--headless` opts out. Driver children (`OKF_AUTONOMOUS=1`) emit public progress and never recursively launch another driver. Existing runs do not hot-load new monitor controls.

A known failure that predates the task may remain only if it is off the task's critical path. Record it under `Known failures` in `status.md` with the command that shows it.

## 9.6 Recovery checkpoint (`status.md`)

**Milestone retrospective.** At L3 milestone close, the orchestrator MUST pass every milestone lifecycle record explicitly to `python3 .ai/scripts/okf.py checkpoint --lessons-from RECORD` (repeat the option for each record) and include the resulting unpromoted lessons in the closing retrospective. Record selection is explicit; branch names and timestamps MUST NOT infer membership. Capturing lessons remains optional, and promotion or retirement into standing rules requires human approval at every tier. A retrospective listing does not override an UNSAFE checkpoint.

`status.md` has the sections `Objective`, `Active task`, `In flight`, `Next step`, `Blockers`, `Known failures`, `Key decisions`, and `Last validation`. Overwrite them with current facts; do not append previous run budgets, custody narratives, authorization recitals or historical next actions. Link retained evidence rather than copying its narrative. It is not a log. Every `handoff` prints it into a fresh session, so `okf.py validate` warns and `okf.py checkpoint` fails (not SAFE) when its body exceeds 6,000 characters; `Last validation` keeps only the current candidate's commands. Compact it at the handoff instead of appending. Keep one history document per task (updated in place), not one per sub-topic or session; fresh sessions load history only by section and only when the next step needs it.

- `Active task` begins with the task ID, or `none`.
- `Next step` names one concrete action that a fresh agent can take without asking anyone.
- `Last validation` lists `<exact command> → PASS|FAIL` lines.
- For a batch, `Active task` remains one currently IN_PROGRESS anchor ID (or `none` once closed), so checkpoint tooling stays compatible. `In flight` records all batch members, branches/owners, dependency waves and provisional integrated heads, and distinguishes focused results from the full gate still pending. `Next step` names the next eligible wave or integrated gate. Put the tested batch commit and command/coverage report in `Last validation`; a context reset resumes this same batch rather than dispatching unrelated work.

**Safe checkpoint.** `okf.py checkpoint` exits 0 only when all of these hold:
- the work tree is clean;
- a committed HEAD exists (handoff always reports the actual branch and HEAD; commit age alone does not invalidate status);
- `Active task` and `Next step` are filled;
- the active task is IN_PROGRESS in the queue;
- the queue has no errors;
- `okf.py validate` reports no errors.

**When to checkpoint:** before actual ownership/context handoff, compaction/session retirement, managed validation, or an interruption that needs durable recovery. Combine source, coherent OKF/log updates and changed execution facts at that boundary. A new claim, each subtask, routine focused command or newer commit does not by itself require another SAFE checkpoint or prose-only commit. While workers run, ownership can be recorded without first committing it; resolve genuine ownership conflicts before dispatch.

Run startup/authorization is already retained in launcher progress. Do not add an OKF log-only commit for it. Unchanged claims and adequate plans need no rewrite or repeated review. OKF synchronization and its log remain mandatory once the coherent implementation/workflow change is ready for handoff or completion.

WIP commits on the task branch are allowed. Prefix their subject with `wip:`. They never reach the default branch (§8.1).

## 9.7 Decisions

Resolve uncertainty in this order: code, tests, the OKF bundle (`okf.py search`), ADRs, then authoritative external documentation (cite it in the bundle). Then decide by tier:

- **Tier A — decide and record.** The choice is local and reversible: internal structure, private interfaces, test layout, choosing between equivalent approaches inside already-selected technology, task decomposition, ID allocation. Pick the most reversible option. If it is architecturally significant, add an ADR with status `Proposed by agent; not reviewed`, then continue.
- **Tier B — block and continue elsewhere.** The choice is gated or consequential: anything the project's ADRs or research gates reserve for qualification or for a human, new third-party dependencies (check license compatibility), breaking public contracts or wire formats, changing security boundaries, removing or materially changing a requirement, deleting user data, and outward-facing actions §9.9 does not grant. Mark the task BLOCKED with the question in `Blocker`, list it in `status.md`, and select other READY work.

Do not reopen an accepted ADR unless new evidence invalidates its assumptions or meets its revisit conditions. When this protocol is active, the Behavioral Guidelines' instruction to "ask" means applying Tier B. Everything else is decided under Tier A and recorded.

**Planning changes.** Agents may split tasks, add discovered work, add missing dependencies, refine sub-criteria, and change priorities. Removing or materially changing a requirement is Tier B. Once a human approves it, record an ADR and update the requirement, roadmap, and queue together.

## 9.8 Context management

Every turn re-sends the whole context, so token cost grows with the turn count multiplied by the context size. Agents cannot measure their own context, and harnesses compact only near the window limit, so resets are structural rather than left to judgement:

- **One session per bounded batch** (solo) **or batch round** (orchestrator). The session ends at §9.5 step 11 with a safe checkpoint. A batch may contain several dependency waves; a context reset can resume the same unfinished batch.
- **The driver starts each session fresh.** `python3 .ai/scripts/autonomy_driver.py [--role orchestrator] -- AGENT_COMMAND` runs the agent non-interactively once per session with the `okf.py handoff --prompt` text, until no task is READY or IN_PROGRESS. Before each session it runs `pr_sync.py` (§9.9), and it stops rather than run without it unless given `--no-pr-sync`. It stops early when the agent fails, when sessions stop making commits or status changes, or at `--max-sessions`. Use the harness that launched the run, with machine-readable output so the driver can relay progress: `-- cursor-agent -p --output-format stream-json --force --trust`, `-- claude -p --output-format stream-json --verbose --permission-mode acceptEdits`, or `-- codex exec --json --sandbox workspace-write`.
- **Interactive supervised sessions** checkpoint and reset context at the §9.2 limits; they are not the unattended runner. Use the bounded driver for unattended work. A clear/new conversation must not reset the recorded qualification count or bypass a circuit-breaker stop.
- **Interactive slices get a fresh conversation.** After a slice is delivered (PR opened, or the user names the next slice), continue in a new conversation started from `okf.py handoff --prompt`. A single thread carried across slices re-sends hundreds of thousands of tokens on every tool call, and compaction does not shrink it to a fresh start.

Within a session, keep context small:
- load docs and personas by section, and this protocol by section;
- read source by line range (`Read` with `offset`/`limit`, or `repo.py read PATH --lines A-B`), never whole files by `grep '^'`;
- send broad searches and long validation runs to subagents that return conclusions, or start long runs with `wait_check.py start` and block with `wait_check.py wait` (never sleep/`tail`/`ps` polling loops);
- batch tool calls: one turn issues every independent read, grep and status command together (several calls in one `exec`/parallel block); a turn with one or two small reads is a defect, since each turn re-sends the whole context;
- steer a subagent at most when its brief was wrong or a decision it asked for arrives; give it one complete brief and take one report, not a stream of nudges, because every message is a full-context turn for the sender;
- never wait by turns: no `sleep`, no `wait` with a 1 s yield, no repeated `tail`. After `autonomy_validation.py submit`, record the result path and next check, then end the turn (or make one blocking `wait_check.py wait` at its default `--max`). Post commentary at phase changes only;
- when a diagnostic fails on observation logic (OCR, parsing, assertions), replay the saved screenshots, logs or captures offline until the observer passes, then rerun the installed flow once; each full installed run costs minutes and finds one fault;
- after a compaction, reuse role, persona and protocol sections already summarized in context instead of reloading their outlines;
- retain concise discoveries with the owned work and synchronize the bundle at its meaningful handoff; do not stop implementation for a separate prose commit after each discovery;
- do not re-read what is already in context;
- the generated handoff prompt already includes the objective and next READY tasks; repeat `handoff` only after state changes or when required recovery detail is missing;
- resolve actual document paths/headings once with `okf.py list/search/show --outline`, then reuse the relevant sections; do not repeatedly load whole roles/protocols or speculate about document paths before dispatch;
- pass head, owned diff, evidence locations and the exact next action in handoffs, without repeating investigation narratives; workers/reviewers use their task brief instead of loading global context;
- trim long command output with `tail`.

If the context still grows large mid-task, typically during a long debugging session, finish the current atomic step, write a safe checkpoint with a precise `Next step`, and end the session; the next one resumes the same task. Never end with an unsafe checkpoint unless the harness forces it. In that case, the next session resolves it first (§9.5 step 1).

**Harness support.**
- **Claude Code:** `.claude/settings.json` runs `.ai/scripts/autonomy_hook.py` on `SessionStart`, so every startup, resume, clear, and compaction begins with the `okf.py handoff` digest injected into context. With `OKF_AUTONOMOUS=1`, which the driver sets, its `Stop` handler blocks ending a session only while the checkpoint is unsafe, up to `OKF_AUTONOMOUS_MAX_CONTINUES` times per session (default 3). Remaining work never keeps a session alive.
- **Other harnesses:** they rely on `AGENTS.md` §6 Gate 1 step 0 and the driver's prompt.

## 9.9 Version control authority

**One milestone, one PR.** Milestones, not tasks or sessions, define PR scope. All of a milestone's implementation, fixes, tests, OKF updates and execution-state records belong to the same PR targeting the default branch. Task completion and session boundaries never create additional PRs.

Agents may create and push internal task branches/worktrees, merge reviewed work into their milestone branch, merge the default branch into it, and open or update the milestone PR without asking. They never merge into the default branch without explicit human authorization.

**Milestone branch and title.** Use `milestone/m<N>` (for example `milestone/m1`) as the integration branch. Start it from the up-to-date remote default branch. Before creating a PR, inspect open PRs and the recovery checkpoint for the milestone; reuse the existing branch/PR, including one with an older branch name, rather than creating a duplicate. The PR title must be `M<N>: <Title>` (for example `M1: Headless foundation and core contracts`); `<Title>` describes the entire milestone's scope, not the latest task. Keep its description current with the overall scope, included tasks, milestone exit criteria, and exact validation commands and outcomes.

**Milestone body checklist.** The PR body must list every feature/task that makes up the milestone from the roadmap and work queue, including pending and blocked work, as a Markdown task list. Include task/feature IDs where available so each item maps to its scope and evidence. Use `- [ ] <ID>: <feature/task>` for incomplete items and `- [x] <ID>: <feature/task>` only after the work is integrated into the milestone branch, review has no unresolved confirmed findings, and required validation passes on the integrated head. Update the body after each task completion or orchestrator round, adding newly identified milestone work and reopening any item that needs further work. Record blockers and exact validation commands/outcomes alongside the checklist. A checked item does not by itself make the milestone PR ready; the full readiness criteria below still apply. In solo mode the implementing agent maintains the body; in orchestrated mode the orchestrator does.

**Merge safety.**
- **Internal task branches.** Branch from the current milestone integration head. Dependent work uses the reviewed dependency after it is merged into that milestone branch. Workers commit and push their task branches and report to the integrator; they do not open task PRs.
- **Execution state has one writer** (§9.1). Task branches never edit the queue, archive or `status.md`. Include the milestone's run-state commits in its integration branch before readiness; do not open a separate run-state PR or mix another milestone's work into this PR.
- **Combine work only by merging branches.** Never cherry-pick, squash, or rebase published task commits into the integration branch. Preserve their ancestry and resolve conflicts before validating the integrated result.
- **Merge the base in; never rebase or force-push.** Before readiness, and whenever the default branch moves, merge it into the milestone branch, resolve conflicts, rerun only the checks whose inputs the merge changed (`AGENTS.md` §8.4, *Reuse evidence*), and push. Pull an existing branch with `git pull --ff-only` before editing because `pr_sync.py` may have pushed a merge.
- **Bundle files merge per entry.** `okf.py git-setup` registers the merge driver for log, index, queue, archive and status files. `okf.py checkpoint` fails until it is registered. Resolve any shared execution-state sections to reflect the actual milestone checkpoint.
- **`pr_sync.py` keeps milestone PRs mergeable.** Before every driver session, it merges the base into milestone PRs that have fallen behind. A real conflict returns a ready PR to draft with a comment listing the files; resolving it is the next session's first job.

**Pull request state is the milestone merge signal.**
- Open the milestone PR as a draft (`gh pr create --draft --title 'M<N>: <Title>'`). Keep it draft across task completions while any milestone work, review fix, exit criterion, or validation remains pending or blocked.
- Mark it ready (`gh pr ready`) only after all milestone tasks and exit criteria are complete, the body checklist reflects that completion, review has no unresolved confirmed findings, required validations pass on the integrated PR head, execution-state records are included, and `gh pr view N --json mergeable` reports `MERGEABLE`. Comment the exact commands and PASS outcomes. One DONE task is insufficient.
- If further milestone work becomes necessary after readiness, return the same PR to draft (`gh pr ready --undo`) and update it. Do not create a follow-up task PR for that milestone.
- A blocked milestone stays draft with its blocker and unblock condition recorded.
- In orchestrated mode, only the orchestrator manages the milestone PR and marks it ready after milestone validation. Workers return branches and reports, not PRs.
- For legacy per-task PRs, integrate their original branches into the milestone branch by merging. Close only agent-owned superseded PRs once their commits are present in the milestone PR, with a comment linking it. Do not delete or rewrite other agents' work.

Agents must not, unless a human explicitly authorizes it for the run:
- merge into the default branch;
- force-push shared branches;
- rewrite published history;
- delete branches they did not create;
- publish releases.

Never use a bare `git stash`. Other agents may share the stash stack, so set work aside with a WIP commit instead. A task may be marked DONE after its reviewed work is integrated and verified in the milestone branch, while the milestone PR remains draft for the remaining work.

## 9.10 Multiple agents

- **Solo mode.** One agent runs the loop. It writes the queue and `status.md` on the run branch, implements on internal task branches, and merges reviewed work and milestone execution state into the same milestone PR.
- **Orchestrated mode** ([`agents/orchestrator.md`](agents/orchestrator.md)). The orchestrator alone writes the work queue and `status.md` on the run branch. Each worker gets one owned task/lane, `okf.py handoff --task ID`, its batch plan and a worktree. Reviewers review focused results; one integrator/validator runs the full required suite on the integrated batch. The orchestrator records per-requirement outcomes and ends after the batch round.
- **Parallel dispatch.** Run independent lanes within an eligible dependency wave (§9.5), with disjoint owned files and mutable resources. Shared prose, schema/registry wiring, test fixtures, installed prefixes and build directories count as ownership surfaces. Parallelize planning/review too when their scopes are independent; serialize overlapping changes and dependent steps.
- **Stale claims.** A claim with no commits on its branch for 24 hours may be released by the orchestrator, which logs the release.

## 9.11 Bootstrapping the queue

When the queue has no tasks:
0. If the objective has no roadmap or testable acceptance, run the analyst role (`.ai/agents/analyst.md`, `AGENTS.md` §2.5 Stage 0) bounded to the first usable flow, and turn its requirements and acceptance checks into queue entries. Skip this when acceptance already exists.
1. Use the handoff objective to locate the current roadmap and acceptance sections once. Investigate the selected flow's source/evidence only as needed to identify a real gap; do not inventory the entire corpus first.
2. Create and claim the first eligible bounded flow with its requirement IDs, acceptance references, prerequisites, owner/worktree and next focused check. Start implementation or dispatch its worker in this session; no bootstrap-only commit, full queue rewrite, SAFE certification or planner round is required first. A planner is warranted only for a named blocking decision.
3. Express phase order through `Depends`. A phase's exit criteria become a task that depends on that phase's tasks.
   Group related requirements into bounded usable flows and record dependency waves, focused checks and a shared full gate; preserve the individual IDs, `Depends` and acceptance rather than replacing them with an opaque batch task.
4. Expand the current and next phase's remaining tasks alongside disjoint worker work, with the orchestrator retaining sole queue/status ownership. Later phases each get one gate task that is decomposed once its phase becomes current. Use source/history evidence to avoid duplicating delivered work; do not declare unverified existing work DONE.
5. Complete scope/dependency records and OKF synchronization at the implementation/integration or actual handoff boundary. Run applicable queue/structural checks and preserve a SAFE checkpoint then. Bootstrap alone is not a session-ending event: continue the first batch under §9.5, unless a genuine blocker or existing context/time limit requires handoff. No required acceptance or dependency gate is waived.

## 9.12 Driver supervision and run controls

Load this section before launching or monitoring `autonomy_driver.py`, and as the orchestrator.

**Visible progress:** the chat launching a driver remains the user's live progress relay. Keep its turn open while the bounded run executes; a PID/log link alone is not a completed launch-and-monitor task. Relay the child orchestrator's public progress messages into chat at phase changes and at least once per minute, stating the task, concrete result or current wait, completed-task count when changed, and next step. This cadence binds only that parent relay; driver children and interactive sessions report at phase changes and wait on long checks as in `AGENTS.md` §8.4. Report failures/circuit-breaker stops immediately. Use one local log/event reader; the parent MUST NOT launch another model or implementation owner to summarize status. It MUST NOT expose reasoning, raw tool/MCP payloads, private evidence or credentials. The CLI cannot post into the parent app conversation by itself: the parent must actively relay its events. If that relay is interrupted, it MUST say monitoring ended and MUST NOT promise background chat notifications after ending the turn. Finish with a self-contained summary only when the bounded run stops or the user explicitly hands off monitoring.

**Enforced monitor handshake:** the driver defaults to requiring fresh `--progress-file` and `--chat-ack-file` paths. It waits for the parent acknowledgement before launching a model, emits local heartbeats every 30 seconds even during tests, and stops the owned agent tree if acknowledgement expires (default 90 seconds). The parent reads new events with `.ai/scripts/autonomy_progress.py read`, posts a visible commentary update, then runs its `ack` action. The parent MUST NOT renew acknowledgements in an unattended loop or before posting the update. `--headless` is an explicit user-selected opt-out, not a launcher fallback. If `OKF_AUTONOMOUS=1`, you are already the driver child: you MUST emit public progress and MUST NOT start another driver or renew your own chat acknowledgement. These acknowledgements are an executable supervisor-liveness control; actual delivery into the app chat is the parent's responsibility.

**Launch routing:** when the user names a milestone, reuse that milestone's existing branch/worktree and objective, even if the chat opened in an older checkout. A stopped owner's name in a checkpoint is not proof of a live writer: verify lifecycle/process evidence and record the authorized takeover. Ask only if actual active ownership remains unresolved, not to choose between the named milestone and unrelated main. Launch in a persistent managed terminal (a short-lived tool shell may discard a bare background job), then verify the actual driver PID, durable log and first agent session's target before reporting success. Milestone-driver PR synchronization is scoped to its own milestone; unrelated milestone conflicts must not divert the requested work.

**Worker lifecycle:** a worker ending is a handoff, not a reason to stop the run. Before closing a live worker, query its current command, head, completed checks and remaining work; relay the answer (or explicitly unknown status) in chat. Do not infer a hang from silence during tests. Stop new dispatch at a checkpoint request, settle ownership, preserve unfinished diffs/evidence and resume with a replacement only after the previous owner is stopped or has released the claim. The driver requests checkpointing after 20 minutes, allows up to three minutes for handoff inside the unchanged run budget, and can use one bounded records/ownership recovery session after a forced timeout or a failed worker that left work. A replacement requires a SAFE checkpoint; unresolved ownership is a blocker. External workers outside the owned process group must be queried and reconciled by the orchestrator.

**Make useful progress promptly:** use one compact plan from the queue's existing acceptance and context. After 120 seconds without observed source edits, the driver requests a concrete progress report through `OKF_PROGRESS_REQUEST`: inspected source/commands, findings and next executable action. Investigation can be useful without edits; this advisory query does not request checkpointing or retire a worker. Continue owned work under the existing session/run limits. Register owned worker worktrees before dispatch with `.ai/scripts/autonomy_validation.py track-worker --worktree PATH`. Prose/status changes do not count as source progress or reset the idle limit. Do not fabricate edits or commit unchanged facts merely to say "deferred; try later." A time budget is not an external dependency; perform the useful executable part now and preserve actual unfinished work at the real handoff.

**Dispatch before paperwork:** reuse an unchanged claim. For a new/changed claim, record only task, owner, worktree and next check before dispatch; a commit, push, full plan/checkpoint rewrite, structural audit or SAFE certification is not a prerequisite to starting the worker. Persist meaningful ownership/plan/evidence changes together at the next source/integration/handoff boundary. Do not create authorization-only log commits, planning-certification commits, repeated custody narratives or `status.md` touch-ups merely because HEAD advanced. Driver progress already records run startup; genuine unresolved ownership still blocks overlapping writers. SAFE is required at actual model handoff/validation submission, not throughout active implementation. Update OKF/log once for the coherent change before that handoff; no completion or evidence gate is waived.

**Run independent checks alongside work:** read-only document audits, environment diagnostics and record preparation can overlap implementation when file/resource ownership is disjoint. Do not wait for a diagnostic merely to begin coding, and do not allocate another model solely to wait on it. The driver's background document audit is advisory over a changing tree, never acceptance evidence; its process group is reaped at session retirement and a stable full audit still gates handoff. Git merges, overlapping writers and tests sharing mutable build/install/scratch resources remain serialized. For an unchanged candidate's validation retry, reuse its committed checkpoint and submit the new command environment directly; do not rewrite records or run global checks just to submit it. Known validation-result follow-ups do not require fabricated source activity; run/session/attempt limits still apply.

**Managed validation:** implementation workers run focused checks. After integration and independent source review, commit a SAFE checkpoint with full validation pending, submit the deduplicated command/coverage plan through `.ai/scripts/autonomy_validation.py submit --plan PATH`, then exit the model session. The driver executes that fixed candidate's gate as a dedicated local validation job outside model-session deadlines. Each command has its own finite timeout and durable log/result; the overall run budget and chat supervision remain binding. Admit commands against actual remaining time after closure reserve, without summing worst-case timeout ceilings. Completed checks remain resumable via `submit --resume RESULT_JSON`, with exact candidate/command/environment fingerprints and verified manifest/log hashes; invalidated jobs cannot supply receipts. No model stays open merely to wait. A fresh session reviews the results and closes delivery; SAFE and validation PASS do not alone authorize DONE. Full-gate processes MUST NOT be launched under the model process group. See the playbook for the manifest contract and retry/stall rules. Existing active drivers do not hot-load this behavior.

**Reduce repeated execution:** use `validation_select.py --base REF` for conservative feedback checks, retaining task-specific acceptance and integrated gates. Where the project has an installed-artifact harness, prepare one clean verified artifact per candidate and reuse it across consuming harnesses. Fresh test state remains mandatory. Managed manifests may set bounded `max_parallel`, explicit `resources` and prerequisite `after` labels; undeclared resources remain exclusive. Prepare the independent acceptance mapping during source review and reuse that context for result review where independence permits. Closure has its own `--max-closure-seconds` target (default 600), bounded by session/run limits. An interrupted closure skips recovery only after evidenced delivery, full SAFE and an exact-HEAD `OKF_CLOSURE_RELEASE` receipt confirming relevant worker release; SAFE alone does not release external ownership. No records-only certification round is required.

**Unattended cost control:** run unattended implementation through `.ai/scripts/autonomy_driver.py`; do not emulate it with an unbounded interactive conversation. Its defaults are a 20-minute session checkpoint target, a 60-minute agent-execution run budget and two sessions without an evidenced DONE task. Handoff and recovery consume that same budget and session cap; interruption counts against the delivery-stall limit. After two failed fresh model-backed qualification cases for one slice, preserve evidence and checkpoint that slice; split independently deliverable work into a separately validated batch. New source freezes/threads do not reset attempts. Circuit-breaker stops override keep-going instructions; agents MUST NOT auto-restart to bypass them. See §9.2 for recovery and interactive-session limits.
