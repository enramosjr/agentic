# Agent Lifecycle (AIDLC)

The adopter knowledge mandate remains binding below; framework-source identity in
`AGENTS.md` substitutes source documentation and Git-scratch receipts for a bundle:

All AI agents working on this project MUST ensure that the Open Knowledge Format corpus (`knowledge/`) remains synchronized with any code, specification, architecture, or workflow changes introduced during execution.

One lifecycle for every task, from a one-line prompt to a fully autonomous milestone. The stages and artifacts never change; the tier (`AGENTS.md` §2.5) sets how much ceremony each stage gets. Load by section: `python3 .ai/scripts/okf.py show .ai/lifecycle.md --section HEADING`.

## Router

1. Pick the tier (§2.5), state it with the persona, and declare it before editing source: `python3 .ai/scripts/lifecycle.py tier L2 --reason "new public behavior" --kind feature`. Hooks deny source edits until you do.
2. Run the stages the tier requires, in order, and record each with `python3 .ai/scripts/lifecycle.py stage NAME ...` (see Recording and enforcement). Each stage has an exit check; do not start the next stage until it holds.
3. Escalate the moment investigation shows a contract, schema, persistence, security, or dependency effect, or an unresolved behavior question. Never downgrade a tier the user set.
4. At L1–L3 close a retrospective before Verify: `python3 .ai/scripts/lifecycle.py learn TEXT --evidence REF`, then `python3 .ai/scripts/lifecycle.py retrospect --lessons 1`, or `python3 .ai/scripts/lifecycle.py retrospect --no-new-lessons REASON`. Report the outcome at delivery. Startup observations are advisory evidence; use `python3 .ai/scripts/lifecycle.py observations --query TEXT` for task-specific retrieval.

| Stage | Role | Artifact | Exit check |
|-------|------|----------|------------|
| 0 Intent | `analyst` | L1 intent note; L2+ spec | No open question changes behavior; every requirement has a failing-closed acceptance check |
| 1 Plan | `planner` | Light or full plan; L3 queue entries | Every spec requirement maps to a step and a check; no open decision hidden in a step |
| 2 Implement | `implementer` | Diff, tests, report | Test-first per `AGENTS.md` §8.6; focused checks pass; no §8.1 item on the critical path |
| 3 Review | `reviewer` | Findings or approval | Pass 1 (spec compliance) clean, then Pass 2 (quality); no Critical or High |
| 4 Verify and sync | implementer | Gate 3 and 4 evidence | `okf.py affected` handled, log entry, §8.4 gate for the tier, `okf.py records` exit 0 |
| 5 Ship | implementer, or orchestrator in L3 | Branch, PR, or checkpoint | Candidate frozen on current base; delivery options below |

## Tiers in practice

| Tier | Intent | Plan | Review | Verify |
|------|--------|------|--------|--------|
| L0 trivial | None | None | Read your own diff | Focused check if one exists; `okf.py affected` |
| L1 small | Three-line note in chat: goal, success check, assumptions | Light plan inline | Self-review of the diff; reviewer optional | Focused checks plus the slice's narrowest E2E when behavior changed |
| L2 feature | Spec by `analyst`, approved by the user | Full plan by `planner` | Independent `reviewer`, both passes | Slice E2E, then the full gate once on the frozen candidate |
| L3 milestone or autonomous | Objective and frozen `Acceptance` on each queue entry (the spec, §9.2) | Batch plan (§9.5); `planner` only for a named blocking decision | Reviewer gates DONE (§9.5) | Managed integrated gate (§8.4, §9) |

Single prompts and autonomous runs differ only in who answers the questions: the user at L1 and L2, a Tier A or Tier B decision (§9.7) at L3.

## Stage 0: Intent

Run the `analyst` role. At L1 write the three-line note and continue. At L2 and above:

1. Restate the request as problem, users, and outcome. Separate requirements from solution preferences.
2. Ask only questions that change behavior, in one batch of at most five, each with a recommended default. Without a human, record each default as an assumption and continue.
3. Write the spec (structure in `.ai/agents/analyst.md`). Persist it at `knowledge/specifications/<slug>.md` with `okf.py new` and `status: draft`. A draft spec is intent, not shipped behavior (`AGENTS.md` §5.2).
4. Consistency check before handoff: run `python3 .ai/scripts/lifecycle.py analyze SPEC` and fix every Critical or High finding (`stage intent` refuses them; a Medium manual check needs a reviewer note later). Then apply the analyst's absence-finding lens: missing scenarios, error paths, contradictions, and terminology drift. Each acceptance bullet leads with a backticked command runnable from the repository root.
5. Get approval. Interactive L2: the user approves the spec. L3: the spec becomes the queue entries' `Acceptance` and is frozen at claim time (§9.2).

## Stage 1: Plan

Run the `planner` role. Success criteria cite spec requirement IDs. Ship the light plan at L1 and the full plan at L2. At L3 the queue entry and batch plan are the plan.

## Stage 2: Implement

Run the `implementer` role on an isolated branch or worktree at L2 and above. Follow `AGENTS.md` §8.6: bug fixes start from a failing reproduction; new logic is written test-first. Commit in slices that each pass their focused checks.

## Stage 3: Review

The canonical reviewer report starts with `# Review Report` and contains `## Verdict`. Save the complete returned Markdown body unchanged, including its title and every section. Existing YAML frontmatter may hold metadata outside the body; replace any scaffold body with the returned report. Do not add a heading, introduction, summary or verdict to its body, or rewrite its content. If the handback is noncanonical, request a corrected complete report from the reviewer; the parent must not reconstruct an independent approval.

At L2 and above the order is OKF sync, then `python3 .ai/scripts/lifecycle.py converge SPEC` (each requirement's acceptance command, run from the approved spec; fix any FAIL), then review, then verify, with no commit in between: the run is bound to HEAD, so a commit, even of records only, makes it stale. Run the `reviewer` role. Pass 1 asks whether the change meets the spec and plan, with nothing missing and nothing extra; at L2 and above it cites the converge result, notes each MANUAL requirement in the report's `## Validation Reviewed` section, and applies the absence-finding lens. Run Pass 2 (correctness, safety, maintainability, tests, completeness audit, knowledge sync) when Pass 1 is clean. Fix Critical and High findings and re-review only the fix.

## Mechanically bound review (opt-in)

Ordinary reviews retain their existing provenance. To request native capture for an L2/L3 task, start a Claude or Codex session with the current project hooks, then run:

```text
python3 .ai/scripts/lifecycle.py review enable --adapter claude --session NATIVE_PARENT_SESSION --report knowledge/history/reviews/NEW.md
python3 .ai/scripts/lifecycle.py review status
```

Use `--adapter codex` for Codex. SessionStart registers an observed parent; it does not establish reviewer capability or approval. The request remains pending until matching native reviewer start and completion arrive. The callbacks bind the native session/runtime, reviewer child identity, hook configuration, source (including Markdown, file modes, symlinks and deletions), approved spec/plan, exact convergence and reviewed evidence. The callback CLI currently requires an identifiable Linux native launcher through `/proc`; unavailable identity, missing handlers or conflicting/untrusted execution evidence refuse qualification. Configuration discovery alone is not native execution proof. Callback execution is trusted within this ordinary-workflow boundary; it does not claim that project trust was granted, or report configured model/effort as execution telemetry.

Enable prepares a fresh pending Review scaffold, indexes, a preparation log and lifecycle record administration before review starts. Adopters use a new path inside `knowledge/`; framework source uses an ignored working path and creates no bundle. A pending scaffold cannot approve anything. Complete current convergence before starting the native `reviewer` subagent. During its active interval, recognized edits, Markdown/deletions and supported protected workflow producers from every actor refuse before effects, even with `LIFECYCLE_GUARD=off` or `OKF_AUTONOMOUS=1`. Read-only inspection and native capture remain available. Capture writes only Git scratch, so bookkeeping is not a workspace edit.

Protected producers include lifecycle mutations/check execution, OKF creation/metadata/log/index/queue writes, installation into the target worktree, PR sync (including trial dry-runs), artifact producers and validation registration/execution/publication. Driver protection covers its write transactions and releases before agent launch/wait; only an actual supported driver invocation receives that exception. Supported direct CLI and public workflow-function paths acquire producer leases before state locking. Synchronous child producers borrow ownership without guard/state lock acquisition. Raw check/producer commands register their process and group before exec, so supervisor exit alone cannot release surviving commands or descendants; original argv, OS launch errors and evidence hashing remain intact. Release/recovery requires all granted producers to stop. Recognized native tools retain invocation ownership until a matching post event; hook-process exit cannot clear it. Literal Git mutations use metadata-only Git probes with the original ordered global options, preserving cumulative `-C` and relative selector semantics separately for each command segment. Unsupported target syntax refuses. Arbitrary shell/Python writes and deliberate local forgery are outside this boundary; changed candidate pins still refuse completion. This is not an OS sandbox.

Standalone literal Python root help for `.ai/scripts/lifecycle.py` (`--help` or `-h`) is a reader and acquires no native writer lease. The exact three-argument invocation may use a normal Python executable name/path, harmless quoting and the installed script's absolute path. This exception does not classify help merely by finding a flag: interpreter options, other script paths, extra arguments, compound shell commands, redirection, substitutions and multiline forms retain the existing classification. A help flag passed to a check or used as a mutation's argument value cannot exempt that producer. Actual argparse root help exits before lifecycle producer admission; no active-review policy, capture or candidate state is published.

Producer registration also coordinates existing tasks with a concurrently requested review. A protected transaction may therefore leave closed owner administration in its exact per-worktree scratch namespace after refusal or a no-op; this does not authorize changes to source, lifecycle/merge/validation receipts, review requests, captures or history. Pure readers remain side-effect-free. Pure invalid-option refusal and installer target/no-effect planning occur before admission. Guard namespaces apply the same disk-backed scratch checks, including symlink resolution, before receipt writes.

Recognized Git file writers include move, restore, clean and apply operations. Explicit Git metadata/work-tree flags and corresponding environment selectors guard resolved worktrees and registered metadata owners. Guard namespace lookup ignores Git target environment overrides. Option-bearing `env` wrappers around Git refuse; literal environment assignments are supported. Opted-in commits refuse alternate Git selectors, global `-c`/`--config-env` and unsupported tree-selection forms; use the ordinary checkout or `git -C` with supported full-index message/signing options. This does not interpret arbitrary shell expressions or Git aliases.

A clean Git probe from the selected physical checkout can prove ownership of its own Git directory, including a primary checkout with a `.git` pointer and separated metadata. Different selected metadata still requires independent owner resolution or refuses. Explicit index, object and common-directory overrides retain their separate checks; the physical witness does not grant authority over them.

After the native reviewer returns the complete canonical report:

```text
python3 .ai/scripts/lifecycle.py review save-report
python3 .ai/scripts/lifecycle.py stage review --ref knowledge/history/reviews/NEW.md
```

Export changes only the reserved report body and preserves prepared frontmatter, indexes and logs. It never repairs a report or manufactures a verdict. An identical export is idempotent; conflicting content refuses. Review records the exact native receipt identity and requires Approved canonical output, unchanged pins and a matching saved body under existing YAML/body-hash semantics. Missing output, replaced runtime/configuration, overlapping intervals, another task/session or reused retired reviewer identity cannot qualify.

Report export may legitimately stale validation whose Inputs include the report (for example inferred Python `**`). Append real passing refresh results after Review: ordinary validation may use a new label, and requirement evidence may reuse its stable `req:ID` label. The original reviewed ledger window remains archived; each publication proves the exact append batch and canonical oldest eviction at the 100-entry limit. Existing failure and requirement-freshness gates still apply. Changing prior evidence, source, approved artifacts or exact convergence invalidates advancement. Every opted-in convergence execution has a distinct identity, even within the same timestamp. Do not rerun convergence to repair report-publication staleness. Verify, Ship, status/completion and commit/PR hooks check mechanical freshness, including under legacy autonomy/bypass settings. Commit also checks staged source/report content and modes; opted-in delivery requires a full-index commit, without path arguments or `--only` selecting a different tree.

For interrupted work, `review abandon --reason TEXT` preserves unsuccessful history. `review restart --report NEW_PATH` reserves a fresh destination and requires a new native reviewer child; optional `--session NEW_PARENT` and `--adapter claude|codex` select another observed parent after a runtime restart. `review status` lists registrations with complete captured runtime identity and configuration, with `runtime_liveness: not_assessed`. A sandboxed command may have a different PID namespace and cannot use host-PID invisibility as evidence that the native process stopped. Discovery and pending enable/restart select registration evidence, including potentially stale registrations; they establish neither a live runtime nor approval. Actual native start/completion must still match captured host birth identity, configuration, task and candidate pins. Late callbacks cannot revive an abandoned invocation. `review recover` explicitly resolves stopped producer ownership and a pending ledger publication: only its exact previous or expected durable window is accepted; any third state refuses. Producer/borrower lifetime checks are unchanged: a live/unresolved producer or borrower prevents recovery. A lost native post event remains unresolved even after host exit: the exact invocation needs qualified terminal proof, so this can block recovery. No timeout or fresh session grants approval or silently returns an opted-in task to ordinary review.

Opt-in is also recorded in lifecycle state and an independent Git-scratch expectation marker. Missing operational capture, marker mismatch or missing capture after a recorded native review refuses advancement, including delivery hooks under legacy bypass flags; losing the journal does not restore legacy behavior. Commit environment restrictions also cover `GIT_CONFIG_*` overrides.

Synthetic callback tests validate the adapter contract; they do not prove native event delivery. Actual Claude and Codex start/stop/report capture must both be verified before this feature is claimed complete. Historical failed evaluations remain failed.

## Stage 4: Verify and sync

Close the L1–L3 retrospective before recording Verify: select existing lessons
with evidence using `lifecycle.py retrospect --lessons 1 2`, or explain the absence
of new lessons with `lifecycle.py retrospect --no-new-lessons REASON`. Commit/PR
and ship gates also require closure, independently of any legacy Verify record.
Include the outcome in the delivery summary.

Do not wrap lifecycle mutations (including converge, run, stage and merge apply)
in `lifecycle.py run`. Invoke them directly. An inherited repository-owner stack
refuses same-repository descendant mutations before their bodies execute, avoiding
lost acceptance/ledger evidence. Read-only inspection, merge --dry-run and
independent fixture repositories remain supported; ancestor ownership is retained.

Run `AGENTS.md` Gate 3 then Gate 4 at the tier's breadth. Run each check with `python3 .ai/scripts/lifecycle.py run LABEL [--inputs GLOB...] -- CMD` (argv, no shell, scratch environment; the ledger keeps exit status, tree and head, never output) and ask `lifecycle.py reuse LABEL_OR_CMD` before repeating one: REUSE means the recorded pass still covers HEAD, RERUN means run it again. At L2 and above `stage verify` requires a current passing ledger entry, fails when the newest entry for the current tree failed, and writes its own note from the ledger (`--note` becomes an optional `agent note:`); L1 keeps `--note`. At L1 and above `stage review` and `stage verify` run `lifecycle.py scan-diff`, which fails on an unwaived stub, `pass` with a deferred-work comment, or "future work" in added lines (waive one with `lifecycle:allow RULE -- reason`), and report weak-test findings without failing. Where a bundle exists, `stage verify` also runs `okf.py sync-check --base <task head>`: every changed file must be covered by a changed doc or listed in `knowledge/project/sync-ignore`, that doc's `verified` must postdate the change, and `knowledge/log.md` must change. Stamp docs with `okf.py stamp verified PATH... --run CMD...`, which runs CMD and stamps only on exit 0. A spec that has shipped is folded into `knowledge/capabilities/` and its status moves from `draft` to `stable`, or to `deprecated` when superseded.

For delta intent, preview and apply the approved spec with `lifecycle.py merge SPEC --dry-run` then `lifecycle.py merge SPEC` before Verify. Run current convergence and the existing gates. Verify additionally requires a completed merge receipt, matching postimages, removed-ID absence and target provenance/bookkeeping. Do not defer the delta fold to post-commit Ship.

## Brownfield deltas

`okf.py onboard` inventories tracked paths into absent draft architecture and repository-inventory documents. It keeps existing documents, runs no code, and makes no runtime or capability claim. An analyst inspects cited implementation/configuration and tests, writes claim-level sources, and obtains human approval before establishing living requirements. Whole-feature specs with legacy `R<n>` IDs and prose capabilities remain valid.

A structured capability has a unique uppercase `namespace`, for example `EXPORT`, and one `## Requirements` section containing `EXPORT-R1` bullets and indented named `- Scenario NAME:` blocks. IDs remain stable; retained removal deltas/receipts reserve retired IDs. Do not convert prose automatically.

A delta names one existing capability in frontmatter `target: /capabilities/export.md`. Its `## Target baseline` body repeats `Target: /capabilities/export.md` and pins each operated ID with `- EXPORT-R1: sha256:<hash>` or `- EXPORT-R3: absent`. Hash the complete UTF-8 block, including continuations/scenarios and its final line terminator, excluding separating blank lines. The mirror protects the path under body-only approval hashing.

Use `## Added requirements`, `## Modified requirements`, `## Removed requirements`, and one Acceptance bullet for each operated ID, plus Constraints, Non-goals, Assumptions and Open questions. Empty operation sections contain `None.`. Removals state a MUST retirement behavior and nonempty `Reason:`. Modified entries replace prose and keep existing scenarios by default. To replace or clear scenarios, include an indented `Scenarios: replace` followed by the complete replacement scenario set (empty clears it). This directive does not enter the capability. Acceptance commands stay in the delta and are executed only by converge.

`lifecycle.py merge SPEC --dry-run` produces the capability diff before approval without writing state. `merge SPEC` requires the active task's approved, unedited delta and passing audit. It appends additions, replaces modifications in place, deletes removals and records the spec source. Only operated blocks are pinned: unrelated prose/blocks remain mergeable. Conflict diagnostics name stale IDs; local draft overlaps are advisory, with unobserved branches outside warning coverage. No remote or other-worktree scanning occurs.

Apply publishes a pending lifecycle merge receipt before replacing the capability, then records one log entry, updates indexes and publishes completion. Rerun the same approved delta after interruption; the receipt permits only before/after states and deduplicates bookkeeping. Third-state edits refuse; restore or resolve the conflict with human review. Completed valid reruns report `up to date` without writes. Merge completes no lifecycle stage. Retain the delta and receipt for provenance; no living tombstones are added. Audit detects drift, not deliberate forgery of both artifacts and receipts.

## Stage 5: Ship

1. Fetch the default branch and merge it into the candidate, then confirm the gate evidence still covers the head (§8.4 reuse rules).
2. Offer the user these options and act only on their choice: open or update the PR, keep the branch, or discard it. Discarding deletes work, so confirm it.
3. L3 delivers through the single milestone PR (§9.9). Agents never merge into the default branch.
4. Remove only worktrees and branches this task created.
5. `lifecycle.py stage ship` closes the record. A later commit or PR for review feedback needs a fresh `lifecycle.py tier ... --new`, or a `wip:` commit.

## Debugging flow

Use for any bug, failing check, or unexpected behavior, at any tier above L0.

1. **Reproduce.** Capture the exact failing command and output. If it is not reproducible, say so and gather evidence before changing code.
2. **Isolate.** Narrow to the smallest failing input, test, or commit. Compare against a passing case.
3. **Hypothesize.** State one cause and the observation that would disprove it. Test it with a read-only probe before editing.
4. **Pin.** Write the failing test or reproduction that fails for that cause (§8.6).
5. **Fix and verify.** Make the smallest fix, show the test green, and run the narrowest regression check.
6. **Stop rule.** After three disproved hypotheses or fixes, stop. Question the design or the assumed surface, then report the evidence and the decision needed. Do not stack patches.

## Recording and enforcement

`lifecycle.py learn TEXT [--stage S] [--evidence REF]` records inert observations in active L1–L3 tasks. Capture alone does not close a retrospective. Before Verify, explicitly run `lifecycle.py retrospect --lessons 1 2` for existing lessons with nonblank evidence, or `lifecycle.py retrospect --no-new-lessons REASON` with a nonblank explanation. Verify and commit/PR/ship guards require closure; historical records without closure remain audit-valid. Outcome, timestamp and lesson numbers or reason persist in the audit record. Task declarations and SessionStart surface a separate advisory observation block (up to five whole entries within 8,192 UTF-8 bytes), ranked by query/task-reason token overlap, recency and source reference; absent matches use a labeled recent fallback. `lifecycle.py observations --query TEXT` retrieves read-only context with evidence, provenance and omission/corruption diagnostics. Observations have no instruction precedence. Report the closing outcome at delivery.

`promote RECORD#N --approved-by human:ID` and `retire RULE_ID --reason TEXT --approved-by human:ID` require human authorization; attribution records claims rather than authenticating consent, and `decision:` is refused. Active approved rules have repository-instruction precedence and are injected at SessionStart within an 8,192-byte UTF-8 block. Missing rules preserve prior behavior; invalid rules emit a diagnostic without partial injection. Identical promotion/retirement retries repair interrupted log/index publication. At milestone close use repeatable `okf.py checkpoint --lessons-from RECORD` for every milestone record and include unpromoted observations in the retrospective. See the learning-loop capability and playbook in `knowledge/` when present; an installed adopter starts without template knowledge.

Hooks (Claude Code, Codex, Cursor) call `lifecycle.py hook`. They deny source edits until the tier is declared and the stages required before Implement are recorded, deny `git commit` (other than `wip:`) and PR creation until Verify is recorded, deny such a commit when it would leave the audit record untracked or unstaged, and inject the Router at session start. Markdown and `knowledge/` edits are exempt. `LIFECYCLE_GUARD=off` bypasses tool gates, and autonomous driver sessions are gated by the work queue instead. Both bypasses still receive approved project rules at SessionStart, without the interactive lifecycle router. An approval is a recorded claim that must come from a user message; the guard raises the cost of skipping a stage and does not prove human consent.

## Assurance status

A structured capability requirement may declare, before its first scenario, at most one indented `- Verify:` line (one backticked command, or `manual` and a reason) and, only with `Verify:`, at most one `- Inputs:` line (backticked repo-relative globs; no absolute or `..` globs). A duplicate line, a line after a scenario, `Inputs:` alone, an empty command or a bad glob makes the requirement INVALID.

`lifecycle.py assure` reports one line per requirement, from the newest `req:<ID>` ledger entry in committed lifecycle records and the active task whose command and inputs equal the current obligation:

| Status | Meaning |
|--------|---------|
| VERIFIED | The entry passed and ledger freshness holds. |
| STALE | An input file changed (named) or the environment changed. |
| FAILED | The entry exited nonzero. |
| UNVERIFIED | No matching entry exists. |
| INVALID | The obligation is malformed. |
| MANUAL | `Verify: manual`; listed, never affects the exit code. |
| UNDECLARED | No `Verify:` line; counts as a failure only with `--strict`. |

`assure --run [ID ...]` executes the selected non-manual obligations through the `lifecycle.py run` path and records one `req:<ID>` ledger entry each; it needs an active task and refuses inside `lifecycle.py run`. `assure --changed --base REV` lists, without running anything, the obligations whose inputs changed since REV. `--run` does not combine with `--changed`, `--base`, `--strict` or `--json` (exit 2, nothing run). `--json` emits `schema_version` 1. Exit 0 when nothing is STALE, FAILED, UNVERIFIED or INVALID, 1 otherwise, 2 for refused input; a report writes nothing.

Judgment, never evidence. A reviewer who cites a MANUAL capability requirement id in `## Validation Reviewed` of an Approved review that a lifecycle record references makes `assure` show an `attested` object (text: a line starting `judgment (attested, not verified):`) with the review, its hash, time and the record's claimed intent approver. Appending `@` and at least 12 hex characters of the requirement block's sha256 pins the citation to that text; an unpinned citation is honored but labeled as not bound to it, and editing a pinned block, including adding `Accept-risk:`, drops the attestation with a `note:`. An edited review, a non-Approved verdict or a record failing ledger audit is not honored and gives a `note:`; a deleted report gives nothing. An indented `- Accept-risk: YYYY-MM-DD by human:<id> - reason` line before the first scenario shows a `risk_acceptance` (active, then expired) beside a STALE, FAILED or UNVERIFIED requirement. Neither changes a status, the `basis`, a `summary` count or an exit code; only a malformed `Accept-risk:` line makes a requirement INVALID. Approvers are unauthenticated claims.

Limits. A VERIFIED status covers only that command on those inputs, not the requirement's full intent. An obligation without `Inputs:` depends on the whole tree (Markdown and `knowledge/` are exempt, as in `tree_hash`), so any other edit makes it STALE. Evidence recorded on commits a squash merge drops shows as STALE. `--run` entries also record the resolved executable, so a committed record read on a machine or Python install with a different executable shows STALE ("runtime executable changed"), for example in CI; rerun `assure --run` there. Records on unmerged branches are invisible, and a schema-valid hand-written record is accepted: the audit detects drift, not forgery.

Mechanical evidence ordering uses recorded UTC completion precision, after exact requirement/argv/ordered-input matching. New `req:` executions from `assure --run`, direct `run req:ID` and matching delta convergence record six fractional digits at command completion; input/runtime fingerprints keep their existing pre-run capture and field presence. Stage times, attestation ordering, ordinary ledger timestamps and general reuse selection are unchanged. Supported completion values are `YYYY-MM-DDTHH:MM:SSZ` or the same UTC form with one to six fractional digits.

Each timestamp describes a half-open precision interval: a whole-second legacy value covers that second, while six fractional digits cover one microsecond. One execution is latest only if its interval begins at or after every other matching interval ends.
