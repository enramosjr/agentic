# Gate 4 Execution Rules (AGENTS.md §8.4)

These rules are normative: `AGENTS.md` §8.4 requires agents to load them before the first Gate 4 run of a task and before launching or repeating any check that takes minutes. The text moved here verbatim from `AGENTS.md` §8.4 so that sessions pay for it on demand. The words MUST, SHOULD and MAY carry the `AGENTS.md` BCP 14 meaning. Load by section: `python3 .ai/scripts/okf.py show .ai/validation-policy.md --outline`.

## Implementation and batches

During implementation, run focused builds, unit/contract tests and acceptance-specific E2Es for the owned change. For related requirements delivered as a batch (§9.5), defer the full expensive required suite to one validator on the integrated batch head, deduplicating shared commands and retaining all required coverage. Workers report deferred commands explicitly; focused PASS results alone never authorize DONE or checked PR items. After a failure, or a change (including a base merge) to tested code, dependencies or build inputs, rerun the affected checks and the invalidated integrated gate. Records-only updates require OKF/index/whitespace checks, without repeating unchanged product suites.

**Interactive (chat-driven) sessions** use the same split. A user turn ("continue", "commit and continue") is not a gate boundary.

**Implementation handoffs are not validation boundaries, and batches are sized to close.** Choose a batch whose acceptance one scoped gate can close within three implementation sessions. The task's `Sessions` count in the work queue enforces this: `okf.py checkpoint` and `autonomy_driver.py` refuse a fourth session, and relaunching with higher `--max-*` flags does not reset it. A SAFE mid-batch handoff retains the IN_PROGRESS tasks, focused evidence, deferred full commands and next source action, without a full gate merely to end the session. When an independently deliverable part passes its own acceptance and review, close it (DONE with Evidence from a scoped gate) instead of holding it for the rest of the batch. A batch that will not close in three sessions MUST be split before work continues; the new tasks start at zero. Acceptance is frozen when a batch is claimed (`.ai/autonomous-execution.md` §9.2). Run the integrated gate when the batch's planned acceptance is implemented and reviewed, or at an explicit readiness boundary; do not defer an acceptance gate required before a dependent action. Existing budgets, circuit breakers and DONE requirements remain binding.

## Test proportionality

**Test proportionality.** §8 requires enough verification to prove the claim, not maximal verification. One E2E per user-visible success criterion; a negative control only where failure would pass silently, one per assertion class; parametrize over variants instead of adding lanes. "Parity" is met by the user-visible checklist, not by porting a prior harness assertion-for-assertion. There is no manual qualification: every acceptance item MUST name an unattended, deterministic command at claim time, and an item that needs real hardware or a person is out of the batch's scope. Acceptance runs on an isolated virtual display, never the user's live one: `shell_guard.py` rejects `DISPLAY=:0`/`:1` and `WAYLAND_DISPLAY`. A task lists at most eight acceptance commands in its queue entry. An environment-dependent check that fails environmentally gets one repair, then moves to a deterministic layer over the same product code, or is dropped from the batch with the dropped scope recorded (`.ai/autonomous-execution.md` §9.2). Agents MUST NOT satisfy §8.1 by adding tests whose only purpose is more evidence.

## Check selection and reuse

- *Each slice:* focused builds and unit tests for the changed packages (`validation_select.py --base REF` picks them) in the edit-test loop, then the narrowest E2E target that exercises the slice's success criteria once, when the slice's edits are complete and its focused checks pass. This satisfies §8.2 for the slice. Agents SHOULD NOT use the repository's full CI command or full E2E suite as the edit-test loop, and MUST NOT rerun an E2E after an edit, commit, or merge that touches none of its inputs. Persona validation commands are whole-repository forms; in the loop, scope them to the changed package or test (`cargo test -p CRATE`, `go test ./pkg/...`, `pytest tests/test_x.py`).
- *Long checks run at boundaries, not in the loop:* a check that takes minutes (an installed-artifact E2E, a soak, a whole-workspace test run) runs once per slice candidate and again only after a change to its inputs. A repair iterates on the narrowest failing test or the short diagnostic, then runs the long check once. If the full gate follows with no change to that check's inputs, it reuses the passing run instead of repeating it. When a slice's only acceptance E2E is a long-duration check, the slice MAY close its loop on the short diagnostic and defer the full-duration run to the full gate; the slice stays provisional, and is not done under §8.2, until that run passes.
- *Fast tier before any full gate:* agents SHOULD run the repository's formatter check, linters/static analyzers (for every language the change touches) and the tests that iterate every registered variant (profiles, registries, generated bindings) on the candidate first. These take seconds; a full gate that fails on something this tier covers wasted its run.
- *Full gate* (full CI command plus the full E2E/regression suite): once per frozen candidate, when marking a PR ready, checking milestone PR items, closing a batch, when the change touches shared surfaces the focused selection widened to, or when the user asks. Opening or updating a draft PR, commits and pushes to the in-progress milestone branch do not independently require it. A non-draft PR requires the readiness gate. Finish edits and review first; if source changes while the gate runs, stop it and run once on the new candidate rather than finishing and repeating.
- *Freeze on the current base:* fetch the default branch and merge it into the candidate before freezing it for the full gate, so a base that moved during development cannot force a second full gate after the first passes.
- *Group like-for-like suites at the end:* regression suites unrelated to the slice's lanes (prior profiles, the full desktop/UI suite) run once, on the final frozen candidate, not after each repair iteration. Intermediate candidates run the failed lane and the lanes whose inputs the repair touched.
- *Reuse evidence:* a passing gate stays valid for a later HEAD when `git diff --name-only <tested-commit> HEAD` touches none of its inputs (source, tests, build files, lockfiles, fixtures), for example records-only commits or a base merge that changes no tested input. Cite the tested commit instead of rerunning. `lifecycle.py reuse LABEL_OR_CMD` evaluates this rule for a check recorded with `lifecycle.py run --inputs`: REUSE or RERUN. Read-only turns (questions, status, PR creation) run no product suites.
- *Justify expensive execution:* before launching or repeating a check that takes minutes, record the acceptance criterion, its input scope, and either the changed inputs or why no valid covering PASS exists. Reuse the existing command/evidence report; do not create another planning or approval round. A new turn, commit, review, worker, or draft PR is not a reason to repeat a check. Coordinate one full-gate owner per integrated candidate; other sessions reuse its report. Unknown dependencies require conservative reruns. Exact-commit qualification remains bound to its tested commit.
- *Spec acceptance (L2+):* `python3 .ai/scripts/lifecycle.py analyze SPEC` gates the spec before approval and runs nothing. `python3 .ai/scripts/lifecycle.py converge SPEC` runs each requirement's acceptance command once per candidate, after OKF sync and before review; `stage verify` requires that run to have no FAIL and to be current (Markdown and `knowledge/` edits do not stale it, but any commit does, because the run is bound to HEAD; commit the record with Verify, or rerun converge after a commit). Converge gives each command the disk-backed scratch environment (`TMPDIR` under the git directory), as `timed_check.py` does. Gate 4 cites a passing converge run of an identical command on the current tree instead of rerunning that command, and converge adds no checks beyond the spec's acceptance commands. The L3 queue rule above (every queued acceptance item names a deterministic command) still binds; a Medium manual-check finding does not relax it.
- *After a long check fails:* reproduce with the narrowest failing test or phase, fix it, pass that, then rerun the long check once. Agents MUST NOT rerun an unchanged failing check to see whether it passes, and SHOULD NOT rerun a passing command on identical inputs.

## Long-duration checks and waiting

- *Long-duration checks* (soaks, sustained capture, timing runs): assert cumulative invariants while running and fail at the first violation, not only at the end. Keep the full duration for the full gate, and give iteration a short diagnostic mode on the same path that can never produce acceptance evidence. Run the lane that failed last first, never rerun a subset a broader lane in the same gate already covers, and run lanes with disjoint resources concurrently (managed manifests: `max_parallel`, `resources`, `after`) rather than as a serial hand-written chain. Keep timing-sensitive lanes on dedicated cores or alone: contention may cause a false failure but MUST NOT yield a pass. Deliberately broken negative controls belong in the full gate; diagnostic iterations MAY skip them. Each lane SHOULD be runnable alone against the same candidate artifact; if a harness makes a passing lane a prerequisite of the failing one, a repair reruns the failing lane's short diagnostic first and the prerequisite after.
- *Waiting on long checks:* start them with `wait_check.py start` (or in the background) and block with `wait_check.py wait --fail <first-failure pattern>`, leaving `--max` at its default (540 s) or the harness's longest single tool call; `--max` below 300 s is a violation, and a shorter value does not make a wait safer, it only buys more turns. Rerun the same `wait` while it reports `running`. Agents MUST NOT poll with `sleep`, `write_stdin` with a short yield, `tail`, `ps` or log reads, or post a progress message per wait: every poll and message re-sends the whole context. A submitted managed gate (§9) is not waited on by a model at all unless the user asked for a live session; record the result path and next check, then end the turn. Report at phase changes (lane started, lane passed/failed, gate result). This applies to interactive sessions and driver children; the once-per-minute relay in §9 binds only a parent chat supervising `autonomy_driver.py`.
- *Records at commit boundaries:* run `okf.py records` once before each commit that touches `knowledge/**`, instead of separate `validate`, `reindex --check` and `git diff --check` calls after each edit.
